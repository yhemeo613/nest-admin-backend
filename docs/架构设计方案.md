# NestJS 企业级后端框架设计方案

> 版本：v1.2　日期：2026-10-12
> 目标：建立一套**可直接落地生产**的 NestJS 后端框架骨架与配套规范，覆盖架构设计、目录规范、编码规范、细粒度权限体系、AI 基础设施、调试与工程化工具链、测试与部署。

---

## 一、设计目标与原则

| 目标     | 说明                                                               |
| -------- | ------------------------------------------------------------------ |
| 可维护   | 严格分层 + 模块化，职责单一，新成员 1 天内能上手                   |
| 可测试   | 依赖注入贯穿始终，单元测试 / e2e 测试开箱即用                      |
| 可扩展   | 业务模块即插即用；基础设施（缓存/队列/存储/AI）可替换              |
| 可观测   | 结构化日志、请求追踪（traceId）、健康检查、AI 调用审计             |
| 一致性   | 统一响应格式、统一异常、统一命名、统一 Git 提交规范                |
| 权限精细 | 权限粒度到**接口级 + 按钮级 + 数据行级**，角色可配置，变更即时生效 |
| AI 就绪  | LLM 能力作为一等基础设施：Provider 可切换、流式输出、用量可控      |

核心原则：**约定优于配置**、**显式优于隐式**、**基础设施与业务隔离**、**前端隐藏只是体验，后端校验才是安全边界**。

## 二、技术选型

| 领域         | 选型                                                                                       | 理由                                                               |
| ------------ | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| 运行时       | Node.js 22 LTS                                                                             | 长期支持，性能与安全性最佳                                         |
| 框架         | NestJS 11（Express 平台）                                                                  | 生态最成熟；高并发场景可切换 Fastify                               |
| 语言         | TypeScript 5.x（strict 模式）                                                              | 类型安全，`strict: true` 不允许关闭                                |
| 包管理       | pnpm                                                                                       | 磁盘效率、幽灵依赖隔离，monorepo 友好                              |
| ORM          | Prisma                                                                                     | 类型安全 Schema 优先；迁移工具成熟（备选 TypeORM）                 |
| 数据库       | PostgreSQL 16（主库，启用 **pgvector** 扩展）+ Redis 7                                     | 向量检索复用 PG，不引入新组件                                      |
| 认证         | `@nestjs/jwt`（Access + Refresh 双 Token）+ Passport                                       | 无状态认证，支持踢人/黑名单                                        |
| **鉴权**     | **自研权限码 RBAC**：`@RequirePermissions` 装饰器 + 全局 PermissionsGuard + Redis 权限缓存 | 天然支持接口/按钮/数据三级粒度，与菜单权限表同源，权限变更即时生效 |
| 校验         | `class-validator` + `class-transformer`                                                    | DTO 声明式校验，全局管道自动执行                                   |
| 配置         | `@nestjs/config` + Joi 启动校验                                                            | 配置缺失时启动即失败，Fail Fast                                    |
| API 文档     | `@nestjs/swagger`                                                                          | 代码即文档，自动生成 OpenAPI                                       |
| 日志         | `nestjs-pino`（pino）                                                                      | 结构化 JSON 日志，性能最好的 Node 日志库                           |
| 队列         | `@nestjs/bullmq`（BullMQ + Redis）                                                         | 异步任务、延迟任务、重试                                           |
| **AI SDK**   | `openai` 官方 SDK（兼容协议接入 DeepSeek/通义/智谱/Moonshot/Kimi）                         | 国产主流模型均兼容 OpenAI 协议，一套代码切多家                     |
| **向量检索** | pgvector（PostgreSQL 扩展）                                                                | 复用主库，减少运维面；规模化后可平替 Milvus/Qdrant                 |
| **文档解析** | `officeparser` / `pdf-parse`（RAG 摄取管道用）                                             | Word/PDF/TXT 解析为文本块                                          |
| 测试         | Jest + supertest + `@nestjs/testing`                                                       | 官方方案                                                           |
| Lint         | ESLint 9（flat config）+ Prettier                                                          | 职责分离：ESLint 管质量，Prettier 管格式                           |
| Git 钩子     | Husky + lint-staged + commitlint                                                           | 提交前检查 + Conventional Commits                                  |
| 容器         | Docker 多阶段构建 + docker-compose                                                         | 环境一致性                                                         |
| CI           | GitHub Actions（或 GitLab CI）                                                             | 检查 → 测试 → 构建 → 镜像                                          |
| 调试         | VS Code `launch.json` + `start:debug`（`--inspect-brk`）                                   | 断点调试应用 / 单测 / e2e                                          |

> 选型原则：每一项都有明确备选与替换成本评估，基础设施通过抽象层注入，业务代码不直接依赖具体库（包括 AI SDK）。
> 鉴权**放弃 CASL**：权限码模型已覆盖接口/按钮/数据三级粒度，避免双权限范式并存带来的认知成本；个别复杂属性级规则在 Service 内用显式条件表达。

## 三、整体架构

### 3.1 分层架构

```
┌─────────────────────────────────────────────┐
│ 接入层  Controller（HTTP/路由/参数解析/SSE）  │  ← 只做协议转换，不写业务
├─────────────────────────────────────────────┤
│ 应用层  Service（用例编排、事务边界）          │  ← 业务规则在这里
├─────────────────────────────────────────────┤
│ 领域层  Entity / Domain Logic                │  ← Prisma schema + 领域方法
├─────────────────────────────────────────────┤
│ 基础设施 Repository / Cache / Queue / AI / 存储│  ← 可替换实现
└─────────────────────────────────────────────┘
```

**依赖方向单向向下**：Controller → Service → Repository。禁止反向依赖，禁止 Controller 直接访问 Repository/Prisma/AI SDK。

### 3.2 模块划分（三层模块体系）

| 模块层     | 目录           | 职责                       | 示例                                                   |
| ---------- | -------------- | -------------------------- | ------------------------------------------------------ |
| 基础设施层 | `src/infra/`   | 全局技术能力，与业务无关   | prisma、redis、logger、queue、ai、storage              |
| 共享层     | `src/shared/`  | 跨业务复用的通用能力       | 拦截器、过滤器、守卫、装饰器、常量、工具函数           |
| 业务层     | `src/modules/` | 一个业务域一个模块，高内聚 | auth、**system（权限中枢）**、user 业务、ai-chat、file |

规则：

- 业务模块之间**原则上不互相 import**；必须通信时通过事件（EventEmitter2 / BullMQ）或上提到应用服务编排。
- `infra` 与 `shared` 只允许被依赖，不允许反向依赖 `modules`。
- `system` 模块是**权限中枢**：用户、角色、权限（菜单/按钮/接口）、部门统一管理，其他业务模块只消费它下发的权限能力。
- **AI 能力只通过 `infra/ai` 暴露给业务模块**，业务代码永远不直接 import `openai` 等 SDK。

## 五、核心横切设计

### 5.1 统一响应格式

所有成功响应由全局 `TransformInterceptor` 包装：

```json
{ "code": 0, "message": "ok", "data": { ... }, "traceId": "req-xxx", "timestamp": 1760313600000 }
```

- `code: 0` 表示成功；业务错误使用**错误码枚举**（如 `10001` = 用户不存在），集中在 `shared/constants/error-code.ts`。
- HTTP 状态码表达传输层语义，业务码表达业务语义，两者不混用。鉴权失败固定：未登录 `401 + 40101`，无权限 `403 + 40301`。
- **例外**：SSE 流式接口与文件下载接口不经过响应包装拦截器（`@SkipWrap()` 装饰器标记）。

### 5.2 统一异常处理

- 全局 `AllExceptionsFilter` 兜底，捕获 `HttpException`、`PrismaException`、未知异常，统一输出错误结构并记录日志（含 traceId、stack）。
- 业务代码只抛 `BusinessException(ErrorCode.USER_NOT_FOUND)`，禁止 `return { code: -1 }` 式错误返回。

### 5.3 认证与授权（概述）

- **认证**：JWT 双 Token。AccessToken 2h + RefreshToken 7d（Redis 存储，支持单点踢人、登出即失效）。
- **授权**：权限码 RBAC，粒度到接口/按钮/数据行，**详见第六章**。密码：`argon2` 哈希；登录限流（`@nestjs/throttler`，按 IP+账号双维度）。

### 5.4 请求处理管线顺序（全局装配，顺序固定）

```
helmet → cors → compression → pino-http(traceId注入)
→ ThrottlerGuard → JwtAuthGuard（验token，挂user） → PermissionsGuard（校验权限码）
→ ValidationPipe(whitelist/transform/forbidNonWhitelisted)
→ DataScopeInterceptor（注入数据范围） → TransformInterceptor(响应包装)
→ AllExceptionsFilter(兜底)
```

### 5.5 配置管理

- `.env.{development,test,production}` 分环境加载，启动时 Joi 校验，缺关键配置直接拒绝启动。
- 代码中**只允许**通过 `ConfigService` 读取，禁止散落 `process.env`。
- AI 配置域独立：`AI_PROVIDER / AI_API_KEY / AI_BASE_URL / AI_MODEL / AI_FALLBACK_MODEL / AI_TIMEOUT_MS / AI_MAX_TOKENS`。

### 5.6 日志规范

- 全链路 `traceId`（异步上下文 `AsyncLocalStorage` 透传），日志输出 JSON，生产环境按天滚动 + 采集到 ELK/Loki。
- 级别约定：`debug`（开发调试）/ `info`（关键业务节点）/ `warn`（可恢复异常，含鉴权拒绝）/ `error`（需告警）。
- 敏感字段（password、token、手机号、API Key）在日志管道中自动脱敏。
- **权限审计日志**：角色分配、权限变更、用户禁用等敏感操作强制落审计表（操作人、对象、前后值、IP、traceId）。

### 5.7 数据库规范

- Prisma schema 为唯一事实来源；表名 `snake_case`，TS 模型 `PascalCase`（`@@map` 映射）。
- 所有写操作迁移通过 `prisma migrate dev/deploy`，**禁止** `db push` 上生产。
- 通用字段：`id (uuid)`、`created_at`、`updated_at`、`deleted_at`（软删除）。
- 事务：跨表写入必须用 `prisma.$transaction`；查询 N+1 通过 `include/select` 审查。
- **pgvector**：向量列使用 `Unsupported("vector(1536)")` 声明 + 迁移 SQL 中 `CREATE EXTENSION IF NOT EXISTS vector`，相似度检索用原生 `$queryRaw`（cosine 距离 `<=>`）。

### 5.8 API 设计规范

- RESTful + 版本前缀：`/api/v1/system/users`；名词复数，动词交给 HTTP 方法。
- 分页统一 `?page=1&pageSize=20`（上限 100），响应结构 `{ list, total, page, pageSize }`。
- Swagger 文档自动生成，`@ApiTags @ApiOperation @ApiResponse` 必写；DTO 即文档源。
- 幂等：写接口支持 `Idempotency-Key` 请求头（Redis 去重）。
- 流式接口：`POST /api/v1/ai/chat/stream`，`Content-Type: text/event-stream`，数据帧格式 `{ "delta": "...", "done": false }`。

## 六、细粒度权限设计 ★

> 设计目标：**权限粒度到接口、到按钮、到数据行**；角色可在线配置，变更秒级生效；前端拿权限码控制渲染，后端 Guard 做最终裁决。

### 6.1 权限模型

经典 RBAC 增强模型：**用户 ←多对多→ 角色 ←多对多→ 权限**，外加**部门树**承载数据权限。

权限（`sys_permission`）分四种类型，一棵树统一管理：

| 类型 type     | 说明                                   | 示例                      |
| ------------- | -------------------------------------- | ------------------------- |
| `dir` 目录    | 前端左侧菜单分组，无独立页面           | 系统管理                  |
| `menu` 菜单   | 前端页面路由                           | 用户管理页 `/system/user` |
| `button` 按钮 | 页面内操作按钮（新增/删除/导出…）      | 用户管理-新增按钮         |
| `api` 接口    | 后端接口权限，与按钮一一对应或独立存在 | `POST /system/users`      |

- 按钮权限与接口权限**共用同一套权限码**：前端按钮的 `v-permission` 与后端接口的 `@RequirePermissions` 用同一个 code，一次分配，前后端同时生效。
- 一个用户可挂多个角色，最终权限 = 所有角色权限码的**并集**。
- 超级管理员（`sys_user.is_super = true`）绕过一切权限校验。

### 6.2 权限编码规范

格式：**`{模块}:{资源}:{动作}`** 三段小写，冒号分隔。

- 标准动作枚举：`list`（分页查询）/ `detail`（详情）/ `create` / `update` / `delete` / `export` / `import` / `assign`（分配）/ `reset`（重置）/ `audit`（审核）。
- 业务自定义动作（如 `ai:chat:ask`）需评审后加入枚举，禁止随意造词。
- 权限码**单一事实来源是代码常量** `shared/constants/permission-code.ts`（`PermissionCode.SystemUserCreate = 'system:user:create'`），装饰器与 seed 脚本只引用常量；启动时 seed 同步入库，保证代码与库里权限树一致。

权限码矩阵示例：

| 页面/功能 | 按钮     | 权限码                       | 对应后端接口                               |
| --------- | -------- | ---------------------------- | ------------------------------------------ |
| 用户管理  | 查询     | `system:user:list`           | `GET /api/v1/system/users`                 |
| 用户管理  | 新增     | `system:user:create`         | `POST /api/v1/system/users`                |
| 用户管理  | 修改     | `system:user:update`         | `PUT /api/v1/system/users/:id`             |
| 用户管理  | 删除     | `system:user:delete`         | `DELETE /api/v1/system/users/:id`          |
| 用户管理  | 重置密码 | `system:user:reset-password` | `PUT /api/v1/system/users/:id/password`    |
| 用户管理  | 分配角色 | `system:user:assign-roles`   | `PUT /api/v1/system/users/:id/roles`       |
| 角色管理  | 增删改查 | `system:role:*`              | `/api/v1/system/roles`                     |
| 角色管理  | 分配权限 | `system:role:assign-perms`   | `PUT /api/v1/system/roles/:id/permissions` |
| 权限菜单  | 增删改查 | `system:permission:*`        | `/api/v1/system/permissions`               |
| 部门管理  | 增删改查 | `system:dept:*`              | `/api/v1/system/depts`                     |
| AI 问答   | 发起对话 | `ai:chat:ask`                | `POST /api/v1/ai/chat/stream`              |
| AI 问答   | 查看历史 | `ai:chat:history`            | `GET /api/v1/ai/chat/sessions`             |
| AI 知识库 | 上传文档 | `ai:doc:upload`              | `POST /api/v1/ai/docs`                     |

### 6.3 数据表设计

```prisma
model SysUser {
  id        String   @id @default(uuid())
  username  String   @unique
  password  String                      // argon2 哈希
  nickname  String
  deptId    String?
  isSuper   Boolean  @default(false)    // 超级管理员
  status    Int      @default(1)        // 1正常 0禁用
  roles     SysUserRole[]
  dept      SysDept? @relation(...)
  @@map("sys_user")
}

model SysRole {
  id        String   @id @default(uuid())
  code      String   @unique            // 角色编码，如 admin
  name      String
  dataScope DataScope @default(SELF)    // ★ 数据权限范围
  status    Int      @default(1)
  sort      Int      @default(0)
  users     SysUserRole[]
  perms     SysRolePermission[]
  depts     SysRoleDept[]               // CUSTOM 范围时指定部门
  @@map("sys_role")
}

enum DataScope {
  ALL                 // 全部数据
  DEPT_AND_CHILDREN   // 本部门及以下
  DEPT                // 仅本部门
  SELF                // 仅本人
  CUSTOM              // 自定义部门集合（sys_role_dept）
}

model SysPermission {
  id       String  @id @default(uuid())
  parentId String?                     // 树形结构
  name     String                      // 显示名：用户管理/新增按钮
  code     String  @unique             // 权限码：system:user:create
  type     PermType                    // dir / menu / button / api
  path     String?                     // 前端路由（menu 时）
  icon     String?
  sort     Int     @default(0)
  status   Int     @default(1)
  @@map("sys_permission")
}

model SysDept  { id, parentId, name, sort, status, ancestors String }  // ancestors="0/1/2/" 物化路径，查子树免递归
model SysUserRole       { userId, roleId, @@id([userId, roleId]) }
model SysRolePermission { roleId, permissionId, @@id([roleId, permissionId]) }
model SysRoleDept       { roleId, deptId, @@id([roleId, deptId]) }     // CUSTOM 数据范围
```

### 6.4 后端实现

**（1）声明接口权限** —— 每个受保护接口必须标注：

```typescript
@Post()
@RequirePermissions(PermissionCode.SystemUserCreate)   // 'system:user:create'
@ApiOperation({ summary: '新增用户' })
create(@Body() dto: CreateUserDto) { ... }
```

**（2）PermissionsGuard（全局注册，JwtAuthGuard 之后执行）**：

```
① 接口标了 @Public() → 放行
② 当前用户 isSuper → 放行
③ 从 Redis 读权限码集合：auth:perms:{userId}
   未命中 → 查库（user→roles→permissions，过滤禁用角色/权限）→ 回填 Redis（TTL 30min）
④ 接口无 @RequirePermissions → 默认要求登录即可访问（登录即放行）
   有标注 → 集合包含该权限码？放行 : throw BusinessException(40301, '无操作权限')
```

**（3）缓存失效策略（变更即时生效）**：

| 触发事件                 | 动作                                                             |
| ------------------------ | ---------------------------------------------------------------- |
| 角色-权限变更 / 角色禁用 | 删除所有挂该角色的用户的 `auth:perms:*` 缓存                     |
| 用户-角色变更 / 用户禁用 | 删除该用户权限缓存；用户禁用额外吊销 Refresh Token（立即踢下线） |
| 权限点本身禁用/删除      | 全量清 `auth:perms:*`（低频操作，成本可接受）                    |

事件通过 EventEmitter2 进程内广播，集群部署时改用 Redis pub/sub。

**（4）数据行级权限 —— `@DataScope()` 装饰器 + DataScopeInterceptor**：

```typescript
@Get()
@RequirePermissions(PermissionCode.SystemUserList)
@DataScope({ deptField: 'deptId', ownerField: 'createdBy' })   // 声明参与过滤的字段
findAll(@Query() query: QueryUserDto, @DataScopeFilter() scope: WhereInput) {
  return this.userService.findAll(query, scope);   // scope 已按当前用户角色算好
}
```

拦截器根据当前用户所有角色的 `dataScope` **取最大范围并集**，生成 Prisma `where` 片段：

- `ALL` → 不加过滤
- `DEPT_AND_CHILDREN` → `deptId IN (本部门 + ancestors 物化路径匹配的所有子部门)`
- `DEPT` → `deptId = 本部门`
- `SELF` → `createdBy = userId`
- `CUSTOM` → `deptId IN (sys_role_dept 配置的部门集)`

Service 收到 scope 后与业务查询条件 `AND` 合并，**数据权限对业务代码零侵入**。

**（5）接口权限自动盘点**：启动时扫描所有 Controller 路由与 `@RequirePermissions` 元数据，输出路由-权限码对照表，发现"受保护接口未标权限码"时打 warn 日志；CI 中用同一扫描器做硬校验（缺失即失败）。

### 6.5 前端按钮级权限

- 登录后前端调用 `GET /api/v1/auth/profile`，返回：

```json
{
  "user": { "id": "...", "nickname": "...", "deptId": "..." },
  "roles": ["admin"],
  "permissions": ["system:user:list", "system:user:create", "ai:chat:ask"],
  "menus": [ { "name": "系统管理", "path": "/system", "children": [...] } ]
}
```

- **按钮控制**：Vue 侧 `v-permission="'system:user:create'"` 指令，无权限直接移除元素；React 侧 `<Auth code={...}>` 组件同理。
- **路由控制**：按 `menus` 树动态生成路由，未授权页面路由不注册。
- **边界原则**：前端隐藏只是体验优化，**后端 PermissionsGuard 才是安全边界**——绕过前端直接调接口同样被 403 拦截。

### 6.6 权限中枢模块（system）接口清单

| 接口                                             | 说明                                                                                              |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `GET/POST/PUT/DELETE /api/v1/system/users`       | 用户 CRUD + `PUT /:id/roles` 分配角色 + `PUT /:id/password` 重置密码 + `PUT /:id/status` 启用禁用 |
| `GET/POST/PUT/DELETE /api/v1/system/roles`       | 角色 CRUD + `PUT /:id/permissions` 分配权限 + `PUT /:id/data-scope` 配置数据范围                  |
| `GET /api/v1/system/permissions/tree`            | 权限树（管理端分配用）                                                                            |
| `GET/POST/PUT/DELETE /api/v1/system/permissions` | 权限点维护（通常仅超管）                                                                          |
| `GET /api/v1/system/depts/tree` + CRUD           | 部门树管理                                                                                        |

### 6.7 一次请求的权限校验时序

```
请求 → JwtAuthGuard（验 AccessToken，req.user = { userId }）
     → PermissionsGuard（读 Redis 权限码集合，比对 @RequirePermissions，不通过返回 40301）
     → DataScopeInterceptor（按角色 dataScope 生成 where 片段，挂到请求上下文）
     → ValidationPipe（DTO 校验）
     → Controller → Service（合并数据范围条件执行查询）
```

## 七、AI 基础设施建设 ★

> 设计目标：**AI 能力与具体厂商解耦**，换模型只改配置不改代码；每一次调用可计量、可审计、可降级。

### 7.1 Provider 抽象层

```
infra/ai/providers/
├── llm-provider.interface.ts    # ILlmProvider 统一接口
├── openai-compatible.provider.ts # OpenAI 及所有兼容协议厂商（DeepSeek/通义/智谱/Moonshot/Kimi）
└── ollama.provider.ts           # 本地私有化模型（内网/离线场景）
```

统一接口（业务只面向它编程）：

```typescript
export interface ILlmProvider {
  readonly name: string;
  chat(params: ChatParams): Promise<ChatResult>; // 同步补全
  chatStream(params: ChatParams): AsyncIterable<ChatDelta>; // 流式补全
  embed(texts: string[]): Promise<number[][]>; // 向量化
}
export interface ChatParams {
  messages: ChatMessage[];
  model?: string;
  temperature?: number;
  maxTokens?: number;
  tools?: ToolDefinition[];
  signal?: AbortSignal;
}
export interface ChatResult {
  content: string;
  usage: TokenUsage;
  finishReason: string;
}
```

- `AiModule` 启动时按 `AI_PROVIDER` 配置装配对应 Provider，并支持 `AI_FALLBACK_MODEL` 备用模型。
- 换厂商 = 改 `.env` 里的 `AI_PROVIDER/AI_BASE_URL/AI_MODEL`，**零代码改动**。
- 新增厂商 = 实现 `ILlmProvider` 接口并在工厂里注册一个 case，业务无感知。

### 7.2 统一 AI 门面（AiService）

业务模块只注入 `AiService`，它负责：

1. **路由与降级**：主模型超时/5xx/限流时自动切换备用模型重试一次，全程记录日志。
2. **超时与取消**：默认 60s 超时（`AI_TIMEOUT_MS`），HTTP 请求中断时通过 `AbortSignal` 级联取消 LLM 调用，避免浪费 Token。
3. **重试**：对 429/5xx 做指数退避重试（最多 2 次），4xx 不重试直接抛业务异常。
4. **计量**：每次调用结束后异步写入 `ai_call_log`（不阻塞响应）。

### 7.3 用量治理与审计

- **审计表 `ai_call_log`**：`traceId / userId / provider / model / promptTokens / completionTokens / costEstimate / latencyMs / status / createdAt`，与请求日志用 traceId 串联。
- **成本核算**：内置各模型单价表（配置化），按日聚合输出用量报表接口（管理端，受 `ai:usage:list` 权限码保护）。
- **限流**：AI 接口独立 throttle 规则（默认每用户 20 次/分钟，可配置），防止刷接口烧钱。
- **内容安全**：入参/出参经过可插拔的 `ContentFilter` 管道（默认实现敏感词 + PII 检测，可接第三方内容安全 API）。
- **预算熔断**：可选 `AI_DAILY_BUDGET`，超支后接口返回明确业务错误码并告警。

### 7.4 RAG 检索增强（基础版）

```
文档摄取：upload → 解析(pdf/docx/txt) → 分块(500字, 重叠50) → embed → document_chunk 表(vector 列)
在线问答：query → embed → pgvector cosine topK(5) → 注入 system prompt → LLM → SSE 流式输出
```

- 向量检索 SQL 封装在 `infra/ai`（`$queryRaw` + `<=>` 算子），业务侧只调用 `ragService.search(query)`。
- 分块策略、topK、相似度阈值均可配置；后续规模化时平替 Milvus/Qdrant，接口不变。
- 知识库文档的增删查走权限码 `ai:doc:*`，普通用户与知识库管理员隔离。

### 7.5 Prompt 模板管理

- 模板文件放 `infra/ai/prompts/`，命名 `{场景}.{版本}.md`（如 `rag-qa.v1.md`），变量用 `{{var}}` 插值。
- 代码中通过 `promptRegistry.render('rag-qa', { context, question })` 使用，禁止在业务代码里拼接 prompt 字符串。
- 模板入库管理，修改需评审（prompt 即代码）。

### 7.6 流式输出（SSE）

- `ai-chat.controller` 的流式接口用 `@Sse()` + `Observable` 返回，内部消费 `AiService.chatStream` 的 AsyncIterable。
- 帧格式统一：`data: {"delta":"...","done":false}`，结束帧 `done:true` 附带 `usage` 统计；错误帧带错误码后主动断开。
- 前端 EventSource/fetch-stream 均可消费；Swagger 中标注为流式接口。

### 7.7 AI 测试策略

- **Provider Mock**：测试环境注入 `FakeLlmProvider`（`test/mocks/`），按 prompt 哈希返回预置响应，单测/e2e 零成本、零外网依赖。
- 流式接口 e2e：用 supertest 读取 SSE 流断言帧序列。
- 真实 Provider 冒烟测试：独立 npm script（`pnpm test:ai:smoke`），不进 CI 主流程。

## 九、编码规范

### 9.1 命名规范

| 对象        | 规则                            | 示例                                    |
| ----------- | ------------------------------- | --------------------------------------- |
| 文件/目录   | `kebab-case`，带类型后缀        | `user.service.ts`、`create-user.dto.ts` |
| 类          | `PascalCase`                    | `UserService`、`CreateUserDto`          |
| 变量/方法   | `camelCase`                     | `findUserById`                          |
| 常量/枚举值 | `UPPER_SNAKE_CASE`              | `ErrorCode.USER_NOT_FOUND`              |
| 环境变量    | `UPPER_SNAKE_CASE` + 域前缀     | `DATABASE_URL`、`AI_PROVIDER`           |
| 数据库表/列 | `snake_case`                    | `sys_user.created_at`                   |
| 权限码      | `{模块}:{资源}:{动作}` 三段小写 | `system:user:create`                    |

### 9.2 编码硬性规则（ESLint 强制）

1. `strict` 模式，禁止 `any`（`@typescript-eslint/no-explicit-any` error）；确需宽松用 `unknown` + 类型守卫。
2. Controller **零业务逻辑**：只做参数装配 → 调用 Service → 返回。
3. 所有异步方法必须标注返回类型 `Promise<XxxResponseDto>`。
4. 导入顺序强制（`simple-import-sort`）：node 内置 → 第三方 → `@nestjs` → 别名 `@/` → 相对路径。
5. 路径别名统一 `@/`（tsconfig paths + jest moduleNameMapper 双配置）。
6. 函数单一职责：超过 50 行或嵌套超过 3 层必须拆分（ESLint `max-lines-per-function` 警告）。
7. 禁止循环依赖：CI 中跑 `madge --circular` 检查。
8. 魔数/魔法字符串禁止：一律提取到 `constants` 或枚举。
9. **权限相关**：
   - 受保护接口必须标注 `@RequirePermissions(PermissionCode.Xxx)`，权限码只允许引用常量，禁止散落的字符串字面量（ESLint `no-restricted-syntax` + CI 路由扫描双保险）。
   - 涉及列表查询的 Service 方法必须接收并合并 DataScope 过滤条件，禁止绕过。
10. **AI 相关**：禁止业务代码 import `openai` 等 SDK（ESLint `no-restricted-imports` 强制），只允许 `import { AiService } from '@/infra/ai'`；禁止在业务代码中拼接 prompt 原文。

### 9.3 DTO 规范

- 入参 DTO：`class-validator` 全字段校验装饰器 + Swagger `@ApiProperty` 合一。
- 出参 Response DTO：显式声明可暴露字段，使用 `class-transformer` 的 `@Exclude/@Expose` **白名单模式**，从源头杜绝密码/内部字段泄漏。

### 9.4 Git 提交规范

- Conventional Commits：`feat: 新增用户导出接口` / `fix(auth): 修复刷新token并发问题`。
- 类型限定：`feat | fix | docs | style | refactor | perf | test | chore | ci | revert`。
- Husky 钩子：`pre-commit` 跑 `lint-staged`（eslint --fix + prettier）；`commit-msg` 跑 commitlint；`pre-push` 跑单测。

## 十三、验收标准

1. `pnpm dev` 一键启动，访问 `/api/docs` 可见 Swagger 文档；**VS Code 按 F5 进入断点调试，单测/e2e 调试配置均可用**。
2. 任意接口响应结构一致；异常响应包含错误码与 traceId。
3. **权限验收**：无 token 访问受保护接口返回 40101；普通角色调 `DELETE /api/v1/system/users/:id` 返回 40301；管理端给角色分配权限后用户**无需重新登录**立即生效；`SELF` 数据范围角色查询列表只见本人数据；`GET /auth/profile` 返回的权限码可直接驱动前端按钮显隐。
4. **AI 验收**：配置 `AI_PROVIDER=deepseek` 后，`POST /api/v1/ai/chat/stream` 可流式返回答案，`ai_call_log` 表产生含 token 用量的记录；切到 `ollama` 零代码改动可用；无 `ai:chat:ask` 权限的用户调用被 403 拦截。
5. `pnpm lint && pnpm test && pnpm build` 全部通过。
6. `docker compose up` 起整套环境，e2e 测试在容器网络内通过。
7. 新业务模块按模板 10 分钟内可创建（提供 `nest g resource` 配套的自定义 schematic 或模板目录）。
